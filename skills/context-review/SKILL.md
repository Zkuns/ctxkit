# 检查与整理项目上下文

检查下一位 agent 能否找到当前状态、理解决策并继续工作。依据文档和任务范围内的证据整理，不把一次维护扩大为全库重写。

## 确定范围

- 优先使用用户指定的库路径或入口，其次使用适用 agent 指令中的路径，再考虑 `CONTEXT_ROOT`。没有配置时只检查已有 `~/context`；无法定位则询问，不新建库。
- 先读导航及指定项目。用户要求全库检查时先盘点入口和链接，再按问题读取正文，避免把所有文件同时加载。
- “检查、看看有哪些问题”默认输出发现；“整理、修正、更新”包含相应范围内的普通文档编辑。已有授权继续有效，不机械增加逐项审批。
- 正常工作中发现接手障碍时可主动检查相关文件；已有局部维护约定且证据明确时直接修正。仅查询或用户要求只读时不改文件，也不因为文档较旧就启动全库清理。

## 重点检查

| 检查点 | 如何判断 |
| --- | --- |
| 当前状态 | 是否同时保留了互相冲突的“当前”结论；是否混淆计划、实现、验证和部署 |
| 来源与时效 | 重要结论是否有可追溯来源；日期标识的是编辑还是实际核验 |
| 接手入口 | 导航能否找到项目；主文档能否找到相关仓库、阻塞和下一步 |
| 链接 | 内部目标是否存在；同名双链是否有歧义；移动后是否留下旧引用 |
| 阅读负担 | 主文档是否堆积重复进度、原始日志、失效步骤或大量可独立的细节 |
| 归属 | 跨项目事实是否写错位置；共享内容是否出现多份互相漂移的副本 |

文档旧不等于事实错，本机路径不存在也可能是另一台机器的入口。区分确认错误、疑似过期、待核验，不按日期或猜测直接删除。

库中有 session 工作摘要时，仅在本次要求或生效约定的维护范围内检查重复 ID、重复来源、时间格式与项目链接。它们描述历史成果，不应被批量改写成项目当前状态；查询或重建视图不改变记录的 `updated_at`。

## 形成可操作的结果

指出具体文件、小节、冲突来源、影响和建议，优先处理会让后续 agent 做错事的问题。没有证据时明确不确定，不为了凑数量制造问题。

如果任务包含整理：

- 保留有效现状，合并重复描述；有价值的旧决策保留历史标签或专题链接。
- 主文档保留目标、当前状态、关键决策、阻塞和下一步；详情确实需要独立维护时才拆分。
- 修复实际确认的断链，回查引用；无法确认目标时保留待修复说明。
- 写入前重新读取目标，兼容并行修改；冲突没有依据就保留待确认项，不悄悄选一边。
- 文档维护不运行历史命令、不盘点所有账号、不触发部署。需要当前运行证据时，按用户任务范围核验。
- 回读修改结果，检查新增链接。最后区分已修正事项与仍需确认事项，提供实际文件链接。

普通文档整理不需要跑项目测试。只有任务另含代码或可执行工具变更时，才使用相应验证。
