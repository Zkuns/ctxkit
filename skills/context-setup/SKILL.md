# 建立项目上下文库

让后续 agent 能找到项目、读取必要背景，并把成果写回固定位置。上下文库是普通 Markdown；不依赖 Obsidian、数据库或某个聊天客户端。

## 定位与接入

1. 优先使用用户本次指定的库路径或入口；其次读取适用的 agent 指令里已声明的上下文库；再考虑进程中已设置的 `CONTEXT_ROOT`。发生冲突时以本次明确指定为准。
2. 用户要求新建且没有已有配置时，可使用 `~/context`。展开为当前机器的实际绝对路径；若该位置已有内容，按接入已有库处理。
3. 先检查目录、已有导航和文档标题。已有入口可能是 `CONTEXT.md`、`README.md` 或 `全局/Obsidian上下文导航.md`，不能只因文件名不同就新建第二套库。
4. 已有库沿用其分类、项目名、链接和元数据。只建立缺少的入口，不移动或重命名已有资料来套模板。

## 新建或登记项目

新库可使用下面的最小布局；只有本次确实涉及的项目才创建目录：

```text
CONTEXT.md
projects/
  project-name/
    PROJECT.md
```

- 总导航说明库的用途、项目入口和按需阅读顺序，保持简短，不装入每日进度。
- 项目以用户的工作目标或产品为单位。一个项目可以关联多个仓库；不要按仓库数量机械拆分。
- 项目主文档记录目标与边界、当前状态、关键入口、决策及原因、证据、阻塞和下一步。只保留有实际内容的章节。
- 使用本次材料和实际读取的资料填充。未知信息写成具体待确认项，不能把模板示例当事实。
- 有可直接访问的源资料时只读核对与本次建库有关的部分；建库不触发部署、账号盘点或历史待办执行。

新建时可参考 [导航模板](assets/CONTEXT.template.md) 和 [项目模板](assets/PROJECT.template.md)。创建文件后再增加导航链接；项目专题只需从项目主文档链接。

用户需要记录会话工作成果时，可在库根目录使用 `sessions/` 保存跨项目摘要，导航只需一个工作记录入口。没有此需求不预建记录文件；项目级读取与写回不依赖这层记录。

## 保持入口可复用

用户要日常自动维护时，使用 [常驻指令模板](assets/AGENTS.context.template.md)，把实际库路径、已有导航路径与可用 Python 路径填好。模板定义接手、阶段写回和会话记录的时机，不要求用户每轮点名 skill。

将其增量合并到用户选定或当前客户端已明确使用的指令文件，保留其他规则；路径、作用范围或是否启用 session 不明确时只询问缺少的信息。普通只读请求不等同于启用持续写入。只建库时交付入口和模板，不擅自改其他客户端配置。

模板应放在客户端实际会加载的位置，不能只放进上下文库后就宣称会自动生效。确认客户端能发现所用 skills；个别 skill 未安装时说明缺少的能力，不自动安装或假装已经执行。验证一次自然语言接手和一次阶段写回，区分实际观察与预期。

## 写入与交付

- 记录文件路径或凭据名称即可，不复制密钥、Cookie、完整环境文件或无关个人资料。
- 新库使用标准相对 Markdown 链接；已有 Obsidian 双链按原习惯维护。仓库外部路径单独标明为本机路径。
- 文档是有日期的知识记录，不等于当前运行环境。`last_updated` 表示编辑日期；只有实际核验过的内容才标核验日期和范围。
- 回读新增和修改的内容，确认链接目标存在、没有未替换的模板占位符。
- 返回库入口、项目入口及已建立的阅读方式。若用户同时给了具体工作，接着完成该工作，不止于建库。
