# 写回项目上下文

让下一次工作能从准确的当前状态继续。记录项目成果及必要原因，不把整段聊天或工具日志当项目主文档。

## 定位和范围

- 优先使用用户指定的库或入口，其次使用适用 agent 指令中声明的路径，再考虑 `CONTEXT_ROOT`。没有配置时只检查已有 `~/context`；找不到入口就询问位置，不另造一套库。
- 先读库导航和相关项目已有文档，再决定更新位置。沿用现有分类、命名、链接和元数据。
- 本次要求保存，或已有明确的项目写回约定，就在该范围内执行，不为每一次普通更新重复确认。单纯读取、讨论、代码修改不自动授权整理全部库。
- 写入内容来自用户材料、本次实际工作和可核对的来源。保存“已部署”的记录不意味着去执行部署。

## 选择要留下的内容

优先保存：目标与边界变化、已完成工作、已确认决策及原因、验证范围与结果、关键入口、未解决问题、下一步。

- 区分计划、已实现、已验证、已部署和用户反馈，不能用“完成”抹平这些差异。
- 假设保留其不确定性。未执行测试就记录未验证，不推测通过；局部通过不外推到整个系统。
- 对有价值的失败尝试保留条件与原因；临时猜测、重复讨论和原始日志通常不进入主文档。
- 用户明确要求保存全文时按要求保留正文，并放在适合承载原始资料的位置。

## 增量更新

1. 找到同主题的已有章节。更新当前状态，保留仍有效的内容；不要仅在文件末尾再追加一个相互矛盾的“最新状态”。
2. 被取代但有价值的决策注明日期和替代原因，必要时移到有明确主题的历史或决策文档，并保留链接。不要每次写回都新建日期文件。
3. 一个任务涉及多个项目时，把各自的事实写入各自项目。共用且值得长期维护的规则可写成一个共享专题，再由相关项目链接。
4. 主文档保持可快速接手；详情足够独立时再拆专题。拆分后保留当前结论、阻塞、下一步及详情入口。
5. 加上必要的来源与日期：已读取的文档路径、代码位置、验证记录或用户本次确认。`last_updated` 是编辑日期，不把整篇旧内容标为本次已核验。
6. 写入前重新读取目标相关章节；若其他工作已更新，合并有效变化，不用旧副本覆盖新进展。无法判定的冲突明确标注待确认。
7. 成功创建新项目后更新总导航；新增专题通常只更新项目入口。文档正文更新不需要让总导航重复一份进度。

## 与会话工作记录衔接

用户要求“这个会话做了什么”时，内容属于跨项目工作摘要；“项目现在是什么状态”属于项目文档。有可用的 `context-log` 时使用它管理摘要，两个 skill 可分别使用，不因为写回项目就自动建立会话记录。

同一任务已要求或授权两种记录时，先更新项目的实际现状，再将成果和真实写回位置放入对应工作摘要。只在成功写回后标记“已写回”；部分项目尚未完成时逐项说明。重试先读现有结果，避免重复追加。

从旧工作摘要提炼项目知识时，先检查项目是否已有更新，不能把历史成果当作当前事实覆盖进去。项目里保留必要的来源链接即可，不复制整份会话摘要。

## 验证写回

- 使用可检查的增量文件编辑；回读改动，检查内部链接和前后状态是否一致。
- 标准相对链接按当前文件解析；Obsidian 双链沿用库的约定。重命名或移动文档时修复受影响的引用。
- 不保存密钥、密码、Cookie、私钥或完整环境文件；写配置位置、凭据名称和用途即可。
- 库和仓库文档是独立副本；只有用户要求同步时才比对并更新另一处，不默认双向覆盖。
- 返回实际更新的文件与关键变化。只记录进展时，不额外运行构建、部署、发消息或发布到远端。

这个 skill 定义写回方法，不是后台计时器。持续写回需要本次任务或启动指令中已有对应约定；关闭聊天后不会因安装了 skill 而自动执行。
